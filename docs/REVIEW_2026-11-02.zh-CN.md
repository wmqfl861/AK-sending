## 一、结论

方向正确。ADR-001 的"服务器只做发现、信令和打洞协调，文件只走设备直连"，以及局域网优先、原始字节、无产品额度、默认与单次保存位置、后续多用户，都与需求逐项对应，约束表述严谨。

主要问题有四个：

1. "尽量轻量化"没有体现：路线按 3–4 名全职规划，仓库文档重复多，真正能约束代码的机制少。
2. 公网无中继直连缺少几项关键手段（IPv6 优先、路由器端口映射、内网候选交换），也缺少对失败率的产品预期。
3. 网络库候选可以收敛：iroh 的打洞依赖 relay，建议排除。
4. "同一 WiFi 自动检测"和移动端后台只有原则，缺具体机制和平台约束。

## 四、主要问题与建议

### 4.1 公网无中继：先定成功率预期，再补提高成功率的手段

[资料] 一项 2022-12 至 2023-01 在 IPFS 网络进行的测量，覆盖 440 余万次穿透尝试、8.5 万余个网络：打洞成功率约 70%（±7.1%），TCP 与 QUIC 无统计差异，成功案例中 97.6% 首次即成功 [S10]。这组数据不含更早阶段（如公网地址识别）就失败的样本，也不是本项目的网络，只用来设定预期：不用中继时，相当比例的公网设备组合会连不上，移动运营商的大内网可能更差。

ADR-001 已经接受这一后果。建议补充以下不违反 ADR-001 的手段，并纳入实测：

- **IPv6 优先** [建议]：没有地址转换，双方同时向外发包即可建立防火墙状态，通常比 IPv4 NAT 更容易直连。候选排序为：局域网候选优先（INV-003），公网候选中 IPv6 优先。
- **路由器端口映射** [资料][建议]：UPnP-IGD / NAT-PMP / PCP。Tailscale 的防火墙文档把开启 UPnP 或 NAT-PMP 列为建立直连的办法，并提示其安全取舍 [S11]。现有方案未涉及。是否默认开启、映射何时撤销，需所有者确认（D3）。
- **同出口识别** [建议]：两端在信令服务器登记时上报本机内网候选；服务器发现两端公网出口地址相同，就提示双方先试内网候选。内网地址属于连接候选，按 PROTOCOL 可经控制面传递，仍须端到端认证后才能传文件。
- **自建 STUN** [建议]：STUN 绑定响应可直接实现在信令服务器里，不依赖境外公共 STUN。这与 TECH_SELECTION"不把未知第三方服务当生产依赖"一致；目标地区的可达性需实测。
- **连不上时的出口** [建议]：沿用 UX 文档的提示"当前网络无法建立设备直连，文件没有上传到服务器"，并给出可操作建议：换网络、开手机热点、启用 IPv6、开启路由器 UPnP，或以自己常开的电脑/NAS 作为接收端（ADR-001 允许）。

### 4.2 网络库：建议排除 iroh，收敛到"QUIC + 自建信令/打洞层"

[资料] iroh 官方说明，其打洞协调经由 relay 进行，连接初期数据也先经 relay，打通后才切换到直连 [S12]。n0 团队 2026-07 提交的 QUIC NAT 穿透草案同样假设两端已能建立一条（经 relay 的）QUIC 连接，再在连接内交换候选 [S13]。也就是说，禁用 relay 后 iroh 就失去了打洞协调的来源，而它的默认流程与 ADR-001 禁止的"先中继后直连"直接冲突。

TECH_SELECTION 列出的网络路线，建议收敛为"QUIC 库＋独立信令/穿透层"：

- **数据通道**：QUIC（Rust 的 quinn）。局域网与公网共用一套栈；TLS 1.3 端到端加密、无压缩；多流并发承载多文件和清单分页。
- **打洞**：信令只交换候选（内网、IPv6、端口映射、STUN 映射）→ 双方约定时刻，用**同一个 UDP 套接字**向对方候选互发探测包 → 收到对方探测后，在该路径上直接进行 QUIC 握手并校验对端公钥。全过程没有服务器位于数据路径上。
- **身份** [建议]：每台设备一对 Ed25519 密钥，在 TLS 中以自签证书（或 RFC 7250 原始公钥）承载，握手后比对已配对指纹。手机之间扫码配对交换公钥；没有摄像头的场景，用短码 + 成熟 PAKE（如 SPAKE2）。
- **WebRTC DataChannel（无 TURN）** [建议]：保留为备选，不建议作主通道。它的 SCTP/DTLS 通道吞吐和 CPU 开销通常不如直接 QUIC，与"不限速"冲突，依赖也更重；如需比较，在 P0 用同一硬件实测吞吐。
- **禁 UDP 网络** [建议]：这类网络中公网直连基本不可行。是否为局域网增加 TCP + TLS 兜底，由 P0 数据决定。

### 4.3 "同一 WiFi 自动检测"的具体机制

`policy.rs` 已经表达"局域网候选可用时优先"，缺的是"如何得到局域网候选"。建议三路并行，以实际连通为准（不比较 SSID，与 BLUEPRINT 一致）：

1. mDNS/DNS-SD 服务广播与发现；
2. 有互联网时经信令交换内网候选（见 4.1 同出口识别），可覆盖组播被屏蔽的网络；
3. 手动输入 IP 或扫码（二维码包含地址、端口、公钥指纹），用于完全离线且组播不可用的场景。

方案中尚未写到的平台约束：

- **iOS / macOS 本地网络隐私** [资料]：iOS 14+、macOS 15+ 首次访问局域网时会弹出授权；Info.plist 需声明 `NSLocalNetworkUsageDescription`，使用 Bonjour 时还要在 `NSBonjourServices` 中列出服务类型。在 iOS 上自行收发 UDP 组播/广播，需要 `com.apple.developer.networking.multicast` 授权；通过系统 Bonjour 浏览或注册已声明的服务类型则不需要。iOS 应用如果在后台、授权尚未确定时访问局域网，会被直接拒绝且不弹窗，因此授权要在前台的首次引导中触发。macOS 程序需用 Apple 签发的身份签名，否则授权状态无法稳定跟踪 [S14]。
  - 结论：Apple 平台的发现走原生 Bonjour（Network framework），不要在 Rust 核心里自行发送组播。
- **Android** [建议]：优先用系统 NsdManager；如果在应用内自行接收组播，需要持有 MulticastLock。
- **AP 隔离** [建议]：酒店、公司、访客 Wi-Fi 常开启客户端隔离，同一 SSID 下设备也互不可达。此时应转入公网候选流程，而不是报"对方离线"。
- **桌面防火墙** [建议]：Windows 首次监听会弹出防火墙提示，网络被标为"公用"时入站常被拦截；Linux 的 firewalld、ufw 同理。诊断界面要给出指引。

### 4.4 移动端后台与存储

- **Android 14+ 用户发起的数据传输任务（UIDT）** [资料]：为用户主动发起的长时间传输设计。需声明 `RUN_USER_INITIATED_JOBS` 权限、显示常驻通知，并在应用可见时调度；没有固定时长上限，但过热、低内存时仍可能被停止，应用需持久化进度以便恢复。Android 13 及以下回退到 WorkManager 的前台服务实现 [S15]。
- **dataSync 前台服务不宜作为主方案** [资料]：应用以 Android 15（API 35）为目标时，dataSync 前台服务每 24 小时合计只能运行 6 小时 [S16]。
- **iOS 26 的 BGContinuedProcessingTask** [资料]：由用户显式操作（如点按钮）发起，切到后台后可继续执行。系统显示进度并允许用户随时取消；任务必须持续上报进度，否则会被终止 [S17]。开发者论坛已有用它在后台上传 7 GB 文件的案例，也暴露了进度上报的问题 [S18]。P2P 套接字收发能否稳定运行，须真机验证；iOS 26 以下仍按"前台传输 + 短暂宽限"设计。
- **Android 保存位置** [资料][建议]：Android 10+ 应用向 `MediaStore.Downloads` 写入自己创建的文件不需要存储权限，可用 `RELATIVE_PATH` 指定子目录；官方文档同时提到，通用非媒体文件更推荐用 SAF [S19]。SAF 的每次文件操作都经过跨进程调用，十万级小文件可能明显变慢。建议默认存到"下载"目录、用户改选目录时走 SAF，两种方式的吞吐在 P0 对比实测后再定。

### 4.5 轻量化

**App**

- 仍建议 Flutter + Rust [建议]。LocalSend 以 Flutter 覆盖五端，说明这条 UI 路线可行 [S20]。Tauri 2 的桌面包体更小，但移动端原生能力（SAF、后台任务、Bonjour）的生态较弱，对本项目不划算。
- 边收边算摘要 [建议]：接收端写盘的同时计算整体摘要（如 BLAKE3），避免传完后把整个文件重读一遍；100 GB 级文件重读一次就要数分钟。块级摘要只用于断点续传时核对已落盘的数据；传输中的篡改和损坏已由 QUIC/TLS 的认证加密覆盖。

**服务器**

- 信令 + STUN 合并为一个小程序 [建议]。不承载文件流量，资源需求很低；仅局域网模式完全不需要服务器。

**仓库与流程**

- 初始化时的 23 份 Markdown 中，有 19 份在重复"禁止中继"相关表述。另有一批初始化上传的过程记录：`reports/GITHUB_*`、`reports/archive/BOOTSTRAP_VALIDATION.zh-CN.md`、`scripts/publish.ps1`、`docs/PUBLISHING.zh-CN.md`、HISTORY 中的 ChatGPT Space 记录、SOURCES 中的 S8/S9。建议合并为约 5 份：README、ADR-001、架构与协议、路线与待办、测试计划；过程记录归档或删除（D4）。
- `config/architecture.json` 只被 `scripts/check_repository.py` 读取，而脚本只是比对它是否等于脚本里写死的值；脚本输出中的 `rust_compilation_executed: false` 也是固定值，与本次实际执行结果不符。它不能约束任何运行代码。建议改用以下机制（D6）：
  - **类型约束**：文件引擎只接受握手与身份校验成功后才能构造的连接类型，不提供公开构造函数；
  - **依赖约束**：`cargo-deny` 禁止引入 relay / TURN 类 crate，在 CI 中执行；
  - **服务端约束**：服务端代码和路由中不存在文件上传/下载及通用转发接口，并由测试锁定；
  - **行为约束**：阻断两端数据路径、保留信令时，传输进度必须停止（把 TEST_PLAN 的 T04 自动化）。

## 五、建议的推进顺序（单人 + AI 开发）

现有路线要求 P0 先完成五端构建、公网无中继实测与 iOS 后台实验，再进入真实传输。如果主要由一人加 AI 推进，建议先做出能用的局域网传输，同时尽早验证最大的风险：

1. **Rust 命令行原型（局域网）**：两台电脑传文件与目录，包含 QUIC、设备密钥、断点续传、摘要校验；测量能否跑满千兆有线与 Wi-Fi。
2. **公网直连探测工具**：在同一核心上加信令、STUN、端口映射与打洞，在家宽、手机热点、公司网等组合中实测成功率。这一步决定公网功能的产品形态，应尽早做。
3. **Flutter 界面**：先 Windows + Android，再 macOS / Linux。
4. **iOS**：前台传输、Files 目录授权、本地网络授权引导、BGContinuedProcessingTask 实验。
5. **其他用户**：一次性邀请（FUTURE_USERS 不变）。

这里不给工期估算；第 1、2 步完成后按实测数据重估。
