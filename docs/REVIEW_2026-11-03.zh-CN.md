## 四、问题（按严重度）

### P1-1 传输参数与会话协议把速度限死了（M1 前必须改）[代码]

- `crates/ak-transport/src/identity.rs` 第 107–109 行：流接收窗口 16 KiB，连接接收/发送窗口 64 KiB。
- `crates/ak-transport/src/session/mod.rs` 第 180–197 行：`send_batch` 每发一个不超过 16 KiB 的块，就停下来等对方的 Ack（`SessionSender` 的注释写明 "One in-flight batch"）。

因此每个往返时间（RTT）最多只能传 16 KiB：

| 网络 | 典型 RTT | 理论上限 |
|---|---|---|
| 有线局域网 | 约 1 ms | 约 16 MB/s（千兆线路的约八分之一） |
| Wi-Fi | 3–5 ms | 约 3–5 MB/s |
| 公网直连 | 约 50 ms | 约 0.3 MB/s |

这与"不限速"直接冲突，TEST_PLAN"达到最小瓶颈有效速率 80%"的目标也无法实现。M0 只传了两块合成数据（32 字节 + 16 KiB），所以测不出来。建议在 M1 计划中明确：

- 窗口按带宽时延积设置（例如连接级数 MiB），总量仍受蓝图 32/64 MiB 的缓冲预算约束；
- 文件正文直接依靠 QUIC 流的可靠有序传输，不做逐块应用层 Ack；应用层确认只用于落盘检查点（例如每 N MiB 同步落盘后确认一次）；
- 验收加入真实千兆有线和 Wi-Fi 的吞吐数据。

### P1-2 超时设计容不下接收方人工确认 [代码]

- 所有操作共用 5 秒超时（`crates/ak-transport/src/lib.rs` 第 44 行）。
- 连接空闲 15 秒即断开，且不发保活包（`identity.rs` 第 113–114 行）。
- 发送端 `send_batch` 在这 5 秒内等待接收端的 Ready，超时就中止整个连接。

结果是：接收方必须在约 5 秒内点"接收"。M0 实验没有暴露这个问题，是因为接收端在开始前已做本机确认，收到请求后立即自动批准（`experiments/platform_probe/native/src/lan/network.rs` 第 111–119 行）。

产品中"对方发来文件，接收方看过后再确认"的流程，在现有参数下无法工作。读取源文件时遇到慢速存储（机械硬盘唤醒、iOS 云端文件按需下载）超过 5 秒，也会断开。M1 需要：

- 连接保活；
- 可长时间等待的确认阶段；
- 按"多久没有进展"判定超时，而不是固定 5 秒。

### P2-1 一个端点只能服务一个配对设备，且必须绑定具体 IP [代码]

- `DirectEndpoint` 绑定时只接受一个 `PairedPeer`，TLS 校验器的信任根也只有这一张证书（`connection.rs` 第 59–75 行）。
- 绑定地址不允许 `0.0.0.0`（`validate_address`，第 32–57 行；地址检查对绑定同样生效，测试 `key_mismatch_and_unspecified_bind_are_rejected` 也断言了这一点）。

产品需要"每台设备一个 UDP 端口，接受任意已配对设备"；蓝图第 3 节也要求 STUN、连通性检查和 QUIC 复用同一个 UDP 端点。绑定具体 IP，还会在 DHCP 换地址、多网卡、IPv6 临时地址轮换时失效。

建议 M1/M2 改为：绑定通配地址（双栈）的单个端点，配合按证书指纹查找已配对设备的校验器。

### P2-2 一个陌生数据包就能打断接收 [代码]

`accept` 收到来源地址不符的连接时，直接返回 `UnexpectedAddress`（`connection.rs` 第 111–114 行）；实验的接收循环遇到这个错误即整体失败（`network.rs` 第 85–91 行）。同一局域网内任何人向监听端口发一个 QUIC Initial 包，就能让这次配对失败。

建议拒绝陌生来源后继续等待，直到超时。

### P2-3 流程卡在实机验收，且与蓝图自身规定矛盾 [代码]

两处规定互相矛盾：

- 蓝图第 35 行（D5）与第 147 行：移动端最小实验"与 M1 并行，必须在**完整 UI 投入前**完成"。
- ROADMAP 第 27 行、HANDOFF 第 33 行、M0_STATUS 第 35 行：下一节点是实机验收，不能提前做 M1。

实机验收的门槛对单人维护者很重：

- 设备：Android API 26 与 37、iOS 15 与 26，各需一台物理设备；
- 操作：断开路由器外网，做 10 次冷启动、10 分钟空闲 CPU 采样，再按 SHA-256 整理证据包；
- iOS：产物未签名，装机还需要 Mac、Xcode 和 Apple ID。

而被测的是一次性实验 App，只传两块合成数据，不是最终产品。

建议按蓝图原意处理：

- M1（桌面命令行局域网传文件，只需两台电脑）现在开工；
- 实机验收与 M1 并行，范围缩到所有者手上现有的设备，在 M3（完整 GUI）之前完成；
- 最低系统版本与资源预算，改用真实 App 测量。

### 模拟器能验证什么 [资料]

| 平台 | 能验证 | 不能验证 |
|---|---|---|
| Android 模拟器（Windows 上的 Android Studio，或 GitHub 的 Linux 云端机器） | 安装与启动；API 26 和 API 37 两个版本；`ACCESS_LOCAL_NETWORK` 权限的允许、拒绝、撤销；SAF 目录授权、重启复用与撤权；切后台、锁屏、杀进程后不自动重启 | 与真实局域网设备互连：每个模拟器位于独立的虚拟路由器之后（地址 10.0.2.x），局域网里的其他设备不能直接连入；真机的内存、CPU、冷启动数据 |
| iOS 模拟器 | 构建、启动、界面与目录逻辑 | **只能在 macOS 上运行**，没有 Mac 时只能放在 GitHub 的 macOS 云端机器上跑；**不支持本地网络隐私权限**（Apple TN3179："The simulator doesn't support local network privacy"）；真机后台行为 |

补充：

- 据 Android 官方文档，模拟器 36.5 及以上版本，多个实例可以接入同一个模拟 Wi-Fi 并相互发现（NSD），可用来自动测试两台安卓之间的发现与连接；但这仍是模拟网络，不等于真实路由器。
- 装到真 iPhone 必须签名。免费账号的真机调试要在 Mac 上用 Xcode 完成。没有 Mac 时，正规途径是付费 Apple 开发者账号（年费 99 美元）：在 GitHub 的 macOS 云端机器上签名打包，再通过 TestFlight 安装。这仍需要一台 iPhone，且属于采购决定，现在不必做。

### 修订后的 E3 [建议]

1. **模拟器测试全部放进 CI 自动执行，不需要所有者手工操作。**
   - Android API 26 与 API 37 模拟器在 GitHub 的 Linux 机器上运行，可开启 KVM 硬件加速；
   - iOS 模拟器在 macOS 机器上运行；
   - 权限允许/拒绝/撤销、目录授权、生命周期等用例写成自动化测试。
2. **局域网双设备验证改用电脑**：两台电脑，或一台电脑加一台桥接网络的虚拟机（虚拟机从路由器获得独立的局域网地址）。这也正是 M1 的验收形态。
3. **模拟器测不了的项目标为"待真机"**：iOS 本地网络权限、手机之间的真实 Wi-Fi、真机后台行为、手机资源预算。它们不阻塞 M1–M3，在对应平台发布前（M4）完成；届时再决定 iOS 的签名途径。
