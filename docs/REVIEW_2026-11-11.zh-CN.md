## 1. 结论

- **main 的"全绿"只在本地成立，GitHub CI 实际是红的。** Rust 任务在第一步格式检查就失败，clippy、测试、文档构建在 CI 上从没跑过。即使修好格式，文档构建还有约 50 处 rustdoc 错误；两个 macOS 任务用的镜像已退役，会一直排队。**先恢复门禁，再做别的。**
- **v1 主线（任务码 GUI 与 CLI）还不能跨 NAT 直连。** 候选地址只有本机 IPv4 和回环，没有 STUN 反射地址，也没有 IPv6，接收端只绑 IPv4。两台设备只要不在同一局域网、又都在 NAT 后（家里电脑↔用流量的手机、两个不同家庭），就没有可拨的地址。现有"跨公网"实测的对端是带公网 IP 的云服务器本身。这是产品承诺（PRD FR-003"公网只设备直连"）与实现之间最大的缺口。
- **注册服务能被单一来源低成本打瘫。** 256 个连接名额在 TLS 握手之前就被占用，握手最长可拖 30 秒；兑换预算 60 次/分钟全服务共享，在查码之前扣减；两者都不区分来源。任务码有 160 位随机，全局兑换上限没有防枚举作用，只留下了拒绝服务面。
- **Android 会把设备私钥带进系统备份和换机迁移**（清单没有关闭备份），与架构文档"私钥不出设备"的约束冲突，修复只需几行配置。
- 代码本身的工程质量不差（见第 2 节）。主要问题集中在**门禁、跨网络能力、服务端可用性、移动端发布配置**，以及两套模型并存带来的维护与审计成本。

#### CR-P1-02　v1 主线没有跨 NAT 直连能力

- **位置**：
  - 候选生成：`crates/ak-ffi/src/task.rs:1138-1153` 与 `crates/ak-cli/src/task_cli.rs:1332-1347`（`local_candidates`：只收本机 **IPv4** 网卡地址，再加 `127.0.0.1`）；写入 endpoint blob：`crates/ak-ffi/src/task.rs:1715-1754`、`:2593`、`:2603`。
  - 接收端绑定：`crates/ak-ffi/src/task.rs:2757`，`DirectEndpoint::bind(0.0.0.0:0)`，只有 IPv4。
  - CLI 只有手工 `--advertise` 公网 IP 的"逃生口"（`crates/ak-cli/src/task_cli.rs:1374-1391`）；GUI 没有对应入口。
  - v1 路径（`crates/ak-session/src/pairing/task.rs`、`crates/ak-ffi/src/task.rs`、`crates/ak-cli/src/task_cli.rs`）没有任何 STUN 调用，只有对已知候选的 `holepunch::probe`。
- **证据** [代码]：两端都在 NAT 后时，交换到的全是对方的私网地址，探测包和 QUIC 都发不过去。
- **证据** [已执行]：`scripts/cross_device_test.sh:13-16`、`:26-29` 的"跨公网"用例中，远端就是注册服务器所在的云主机（`--ssh-host` 与 `--server-host` 同为 122.51.121.24），脚本把它的公网地址追加为远端候选。W→L 是直接拨公网 IP；L→W 依赖前一次流量在 Windows 侧 NAT 上留下的映射。这验证了"一端有公网 IP"的情形，没有验证 NAT↔NAT 穿透。HANDOFF 对此有如实标注，但 `README.md:33`"跨公网邀请码配对双向传输已验证"容易被读成穿透已验证。
- **影响**：日常最常见的两种场景（家里电脑↔用流量的手机、两个不同家庭）无法直连。按 ADR-001 只能等待，用户看到的就是"连不上"。
- **可复用的现成组件** [代码]：
  - `ak_signal::stun::query_on`（`crates/ak-signal/src/stun.rs:243`）：在指定 socket 上做 STUN 查询；
  - `DirectEndpoint::bind_with_socket`（`crates/ak-net/src/lib.rs:372`）：把打洞用的 socket 交给 QUIC，保住 NAT 映射；
  - `ak_net::holepunch::bind_dual_stack_udp` 与 `probe`（`crates/ak-net/src/lib.rs:1074`、`:1114`），以及 `DirectEndpoint::bind_dual_stack`；
  - 生产服务器已在运行旧 signal-server 的 STUN（UDP 7101，见 `docs/HANDOFF.zh-CN.md:49`）。
- **改法** [建议]（分三棒；不涉及中继，符合 ADR-001"服务器可做 NAT 穿透协调"）：
  1. **IPv6**：接收端改为双栈绑定；候选加入全局单播 IPv6（排除链路本地 `fe80::/10`）。国内家宽和移动网络的 IPv6 覆盖率高，这一步可能是投入产出比最高的。
  2. **STUN 反射候选**：在 QUIC 将要使用的同一个 UDP socket 上做 STUN 查询，再用 `bind_with_socket` 把这个 socket 交给 QUIC，把反射地址写进 endpoint blob。STUN 地址与注册中心一起配置。
  3. **双向同时探测**：配对完成后双方同时向对方全部候选发探测包；任一方向收到，就用观测到的来源地址建 QUIC。
  4. 两端都是对称 NAT 时，不中继基本无解，UI 要给出明确提示（原 D2 文案）。是否启用 UPnP / NAT-PMP / PCP 端口映射由所有者决定（第 8 节 E3）。
  5. 如果需要改 endpoint blob 的格式或候选上限，先改 `docs/contracts/protocol-v2.md` 的 §10a。
- **验收**：
  - 单元/集成测试：候选列表包含 IPv6 与 STUN 反射地址，并有排序测试；STUN 查询与 QUIC 共用同一 socket 的测试（本地 STUN 服务 + 环回）。
  - 实测（需要所有者的设备；**模拟器、同一宿主上的双进程都不算**）：至少覆盖"家宽电脑↔手机移动数据"和"两个不同家宽"两组，记录 IPv4/IPv6、NAT 类型、是否成功、建连耗时；同时抓包证明数据只在两端之间流动（L3）。结果写进 `docs/TEST_PLAN.zh-CN.md` 对应条目。

#### CR-P1-03　注册服务可被单一来源低成本打瘫

- **位置**：`crates/ak-signal/src/server_v2/engine.rs:82`（TLS 握手超时 30 s）、`:90`（`MAX_LIVE_CONNECTIONS = 256`）、`:94`、`:182-189`（accept 时就占名额，早于 TLS 与身份认证）、`:499-505`（全局兑换窗口）、`:1039-1041`（同一 device_id 的新 Hello 直接顶掉旧连接）、`:1457-1483`（兑换先扣"每连接"和"全局"预算，再查码）；`crates/ak-signal/src/server_v2/config.rs:15`（每连接 10 次/分钟）、`:17`（全局 60 次/分钟）；`crates/ak-identity/src/invite.rs:14`、`:46`（码含 20 字节即 160 位随机）。
- **证据** [代码]：
  - **连接名额**：任何人建一个 TCP 连接就占一个名额，不完成 TLS 也能占满 30 秒。256 个名额用满后，合法客户端只能被拒或被直接断开。来源 IP（`peer_ip`）只用于同出口提示（`engine.rs:2360-2361`），没有参与限流。
  - **兑换预算**：设备身份由客户端自己生成。Hello 证明连接方持有该身份的私钥（签名绑定本次 TLS 连接、单次挑战和时间戳，`engine.rs:983-1025`），但不要求身份事先登记。每个身份同时只能有一条连接，但身份可以随意生成：6 个身份 × 每连接 10 次/分钟 = 60 次/分钟，就能让全服务所有的加入请求都收到 `RATE_LIMITED`。
  - 码有 160 位熵，在线枚举本来就不可行，全局兑换上限起不到防枚举的作用。
- **影响**：一台普通机器（每秒约 9 个不完成握手的 TCP 连接，或 6 个自生成身份持续兑换）就能让所有用户无法生成或加入任务码。已建立的文件直连不受影响，新任务全部受阻。这与 R36-P1-03（名额泄漏，已修）是两个问题：那是名额回收，这里是名额本身不分来源。
- **改法** [建议]：
  1. **按来源限额**：每个来源（IPv4 按 /32，IPv6 按 /64）设并发连接上限（例如 8）和握手中连接上限（例如 4）。在 accept 时检查，超限直接断开，不 spawn 任务。
  2. 缩短握手期限（例如 TLS 10 s；首帧期限已是 15 s）。
  3. 兑换预算改为按来源和按设备身份计数，状态放在共享表里、跨重连保留、带 TTL 回收。全局只留一个很高的熔断值（或去掉），只把"查无此码"的失败计入惩罚。
  4. 可选：限制单一来源创建新身份的速率，或要求新身份首次 Hello 附带小工作量证明。
  5. 同步更新 `docs/SECURITY.zh-CN.md` 的限速说明，以及 `docs/contracts/pairing-flow.md` §11。

#### CR-P1-04　Android 私钥会随系统备份和换机迁移离开设备

- **位置**：`flutter_app/android/app/src/main/AndroidManifest.xml:7-9`（`<application>` 没有设置 `android:allowBackup`、`android:dataExtractionRules`、`android:fullBackupContent`，`res/xml/` 目录也不存在）；身份目录解析为 `getApplicationSupportDirectory()/.ak-sending`（`flutter_app/lib/services/ffi_simple_transfer_service.dart:34-35`、`:71-72`），在 Android 上就是应用的 `files/` 目录；`docs/ARCHITECTURE.zh-CN.md:35` 写明"私钥不出设备……私钥暂为用户目录种子文件，未接系统安全存储"。
- **证据** [资料]：目标 API 23 及以上的应用默认参与自动备份，`getFilesDir()` 下的文件默认包含在内（只有 cache、code_cache、no_backup 除外）。目标 API 31 及以上时，在部分厂商机型上 `allowBackup="false"` 只关云备份、**不关设备间迁移**，要用 `dataExtractionRules` 的 `<device-transfer>` 显式排除。

  1. `<application android:allowBackup="false" android:fullBackupContent="@xml/backup_rules" android:dataExtractionRules="@xml/data_extraction_rules" ...>`。新建两个 xml：`data_extraction_rules.xml` 的 `<cloud-backup>` 与 `<device-transfer>` 两段都排除全部域；`backup_rules.xml`（API 23–30 使用）同样全部排除。
  2. 中期：把身份目录移到 `noBackupFilesDir`（系统总是排除它）。长期：用 Android Keystore 包裹私钥。两项都登记进 BACKLOG。
  3. 已安装的用户升级后身份不变，不需要迁移代码。
- **验收**：`aapt2 dump xmltree --file AndroidManifest.xml <apk>` 能看到三个属性；模拟器上 `adb shell bmgr backupnow dev.ak.ak_sending_app` 后，备份内容不含身份文件（或显示备份已禁用）；Flutter 测试与 APK 构建通过。

#### CR-P2-01　依赖漏洞，且 CI 没有依赖审计

- **位置**：`Cargo.toml:47`（`rusqlite 0.32`，`bundled` → `libsqlite3-sys 0.30.1`）；`crates/ak-cli/Cargo.toml:17` 让发布的 CLI 链接这份 SQLite，线上 `registry-server` 用的就是它；`crates/ak-store` 的 `sqlite` 特性同样受影响。

#### CR-P2-03　targetSdk 随 Flutter 浮动，没有为 Android 17 本地网络权限做准备

- **位置**：`flutter_app/android/app/build.gradle.kts:23`（`targetSdk = flutter.targetSdkVersion`）；Flutter 版本没有固定（见 CR-P2-06）；清单只声明了 `INTERNET`。
- **证据** [资料]：Android 17（API 37）起，目标 SDK ≥ 37 的应用访问局域网（TCP 收发、UDP 单播/组播/广播、mDNS 与 `NsdManager`）需要运行时权限 `ACCESS_LOCAL_NETWORK`（属于 NEARBY_DEVICES 权限组）。没有授权时，TCP 多表现为超时，UDP 返回 EPERM。

#### CR-P2-04　QUIC 全用默认参数：空闲 30 秒、无保活，与确认窗口贴边；公网单流吞吐受限

- **位置**：`crates/ak-net/src/tls.rs` 与 `crates/ak-net/src/lib.rs` 没有任何 `TransportConfig` 设置。quinn-proto 0.11.19 的默认值（`src/config/transport.rs:366-379`）：`max_idle_timeout = 30 s`，`keep_alive_interval = None`，单流接收窗口 1.25 MB（按 100 ms RTT、12.5 MB/s 推算）。确认窗口：`crates/ak-ffi/src/task.rs:214`、`crates/ak-cli/src/task_cli.rs:67`，都是 30 s；发送端空闲预算 `crates/ak-ffi/src/task.rs:225` 为 120 s。
- **证据** [代码]：等待接收方点"接受"期间连接上没有流量。QUIC 的空闲上限和确认窗口都是 30 s，发送端 120 s 的空闲预算实际用不上，QUIC 会先断。确认窗口也因此没法加长。

- **改法** [建议]：在 ak-net 构建 server/client 配置时显式设置 `TransportConfig`：`keep_alive_interval`（例如 10 s）、`max_idle_timeout`（例如 60–120 s）；`stream_receive_window`、`receive_window`、`send_window` 按目标带宽时延积设定（例如 8–16 MiB，计入内存预算）。集中成一张带注释的常量表，并用测试锁定。之后由所有者决定确认窗口时长（第 8 节 E2）。另在 release 深测里加一项模拟公网时延的吞吐基准（Linux `tc netem` 加 50 / 100 ms 延迟）。
- **验收**：新测试断言这些配置值；确认窗口调长后，"接收方 90 秒后才同意，仍能完成传输"的集成测试通过；netem 基准记录调整前后的对比。

#### CR-P1-06　IPv4 下两端都是 Linux 型端口受限 NAT 时打洞失败：conntrack 元组冲突改写了发送端外部端口

  3. 正常 TTL 的打洞保留为后备，用于行为与 Linux 不同的 NAT；IPv6 没有 NAT，打洞保持正常跳数限制。
  4. 运营商级 NAT（两层 NAT）需要的 TTL 更大，TTL 取值要通过 C4 真机数据确定。
  5. 矩阵在 r1 与 r2 之间增加一个"公网"路由命名空间，使 TTL 过期可以被模拟（见 CR-P2-14）。

#### CR-P2-14　NAT 矩阵的证据有缺陷：IPv6 旁路、拓扑竞态、缺少夹具自检

- **位置**：`scripts/nat_matrix_test.sh:199-230`（所有案例都配置并转发 IPv6）、`:447-450`（只有 v6 案才加 ip6tables 规则）、`:457-464`（三个 IPv4 NAT 案都传 `use_v6=0`）、`:184-195`（每案用相同的接口名重建 veth）、`:412-416` 与 `:424-425`（只有 `pass-v6` 案检查 connected-via，预期失败的案意外成功时不打印路径）。
- **证据** [已执行]：
  - CI run 43186738509 与 43231694984 中，pcone↔pcone 都经 `[2001:77:1::2]` 通过；纯 IPv4 内核复跑时 pcone↔pcone 失败、symm↔symm 按预期失败。
  - 本机复现了"An interface with the same name exists in the target netns"，CI run 43188955077 中有两案因此报"base topology broken"，交接没有列出这次 run。
- **影响**：矩阵把 IPv6 直连记成了 IPv4 打洞的成功，把 IPv6 旁路误判为"对称 NAT 模拟保真度问题"，还会随机失败。
- **改法**：
  1. IPv4 NAT 案在两台路由器上设 `ip6tables -P FORWARD DROP`（或者不配置 IPv6 地址），新增 `pass-v4` 期望，断言 connected-via 是对端路由器的核心地址。
  2. 每案使用唯一的接口名，或者删除命名空间后轮询，等旧接口消失再重建。
  3. 每案开跑前做夹具自检：用同一个 socket 向两个不同目的地发包，比较对端看到的源端口。pcone 和 fullcone 必须相同，symmetric 必须不同，否则判为"夹具无效"。
  4. 所有案例都打印 connected-via；任何失败都自动导出两台路由器的 conntrack 表。
  5. 在 r1 与 r2 之间增加一个"公网"路由命名空间。
  6. CR-P1-06 修复之前，pcone↔pcone 标为严格 xfail（关联 CR-P1-06；若意外通过则报红），修复后改为 `pass-v4`；symm↔symm 保持"必须干净失败"。
- **验收**：CI 连续 5 次运行结果一致；夹具自检全部通过；symm↔symm 干净失败；pcone↔pcone 为严格 xfail。

#### CR-P3-09　发送端按公告顺序逐个拨号，每个候选最多等 10 秒

- **位置**：`crates/ak-ffi/src/task.rs:3349`、`crates/ak-cli/src/task_cli.rs:1688`（`for` 循环按 `dial.order` 依次拨号），单个候选的上限是 `crates/ak-session/src/pairing/task_net.rs:90`（`TASK_CONNECT_BUDGET = 10 s`）。

## 6. 门槛命令

在仓库根目录执行。Windows PowerShell 中设置环境变量用 `$env:RUSTDOCFLAGS = "-D warnings"`。

```sh
# Rust
cargo fmt --all -- --check
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo test --locked --workspace --no-fail-fast
cargo test --locked -p ak-store --features sqlite
cargo test --locked -p ak-signal --features server-persistence
RUSTDOCFLAGS="-D warnings" cargo doc --locked --workspace --no-deps
cargo audit                      # 需先 cargo install cargo-audit --locked

# Python（仓库结构、Markdown 相对链接、依赖封禁、契约）
python scripts/check_repository.py
python -m unittest discover -s scripts/tests -v
python scripts/check_contracts.py

# Flutter / Dart（改到 flutter_app 或 FFI 导出时必跑）
cd flutter_app && flutter analyze && flutter test && cd ..
cd flutter_app/packages/ak_ffi_dart && dart test && cd ../../..

# Android（改到 flutter_app/android、ak-ffi 或其依赖时必跑）
bash scripts/build_android_ffi.sh
cd flutter_app && flutter build apk --debug && cd ..
```

每批结束时还要确认 **GitHub Actions 对最新提交为绿**（`gh run list -b dev/review-fixes-20261111`）。本地通过不能代替 CI 通过。

**每批结束时的汇报格式**：

1. 完成的编号及对应提交；
2. 门槛结果（每条命令的通过/失败计数，以及 CI run 链接）；
3. 未执行的项及原因；
4. 复核后判定"不成立"的项及理由；
5. 需要所有者决定的问题。
