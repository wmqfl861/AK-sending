## 1. 阻断发现

### K-R1 / P1：预编译部署在停止服务后复制同一个文件

`scripts/deploy_linux.sh:651` 在 `--binary` 模式将 `SRC_BIN` 设为 `/opt/ak-sending/ak-cli.new`；`:700` 再执行 `install -m 0755 "$SRC_BIN" /opt/ak-sending/ak-cli.new`。源与目标相同，GNU install 报错。此时 `:692` 起已经停止 registry/STUN 服务，`set -e` 会在重新启动之前退出，留下停服状态。即使上传和版本预检成功，也必然遇到此安装错误。离线复现结果见交接证据表。

修复要求：上传到独立的暂存路径，完成权限、版本与可执行性检查后再进入服务切换；对预编译路径增加实际执行安装逻辑的隔离验证，并覆盖失败后的服务恢复。

### K-R2 / P1：保留旧 ExecStart 的可执行文件路径，可能把旧版本当作升级成功

`scripts/deploy_linux.sh:943` 原样保留已有 `ExecStart`；缺少 `--id-dir` 时，`:946` 也只追加参数。若旧服务使用 `/usr/local/bin/ak-cli registry-server ...`，新的文件只安装到 `/opt/ak-sending/ak-cli`，systemd 仍运行旧文件。`:797` 的版本检查却执行新安装路径；日志检查只匹配版本输出的标签，不比较运行中服务的 SHA。因此脚本可输出部署成功，但 registry 实际没有升级。

修复要求：保留身份和数据库参数，同时把可执行文件更新为已验证的新路径；核对实际运行服务的版本与目标提交。还需在默认非 root SSH 用户下验证安装路径的写入权限、已有进程和私有身份目录的发现。

### K-R3 / P2：两个 Paramiko 后端将零超时误用为无限等待

`scripts/deploy_linux.sh:281` 与 `scripts/cross_nat_test.sh:344` 调用 `exec_command(..., timeout=0)` 后立即读取 stdout。Paramiko 的零超时表示非阻塞；命令输出或 EOF 尚未到达就会抛出 `TimeoutError`，使密码认证后端失败。用真实 Paramiko Channel、仅替换网络连接的离线测试已重现两个嵌入 helper 的失败。

修复要求：采用明确的阻塞或有界等待语义，并正确排空 stdout/stderr；将延迟输出与空输出命令纳入离线执行测试。

### K-R4 / P2：Windows runner 漏采传输和校验状态仍可通过

`flutter_app/integration_test/k1_windows_theme_shots_test.dart:325` 的 `verifyingShot` 初始为 false，截图传输阶段后置 true，截图校验阶段后又置 false。若采样直接看到结果卡，`:345` 提前退出时变量仍为 false，`:347` 的断言通过；末尾仍声称已导出完整截图集。

修复要求：分别记录传输、校验截图是否成功，成功退出前要求两项均成立，并检查目标文件。此反例来自代码路径推演，未执行修改过的集成 harness；仓外既有截图集存在，不能据此断言那次走查实际缺图。

### K-R5 / P2：Windows runner 校验的端点与应用实际读取的端点不一致

修复要求：校验最终生效的配置，并将同一份已验证配置传给应用和 CLI。覆盖编译期本地值与运行期非本地值冲突的拒绝路径。本轮没有因此连接生产服务。

## 2. 其他审查结论与证据边界

- ak-net 的前置发送轮在接收分支之前执行，保留了候选过滤、瞬态错误处理和包格式；`interval_at` 避免重复的首拍，`biased;` 明确到期、发送、接收的顺序。预缓冲测试有 `peek_from` 前置条件，既有早退时间约束保留。探测结果仍不等于对端身份或真实路径的认证。
