## 1. 阻断发现

### K2-N1 / P1：恢复保护在写 unit 之前结束，后续失败仍留下停服状态

`scripts/deploy_linux.sh:1008` 的 `do_switchover` 停止 registry/STUN 后，只保护二进制安装；`:1022` 的恢复分支在 `:1026` 结束。随后停止 legacy 服务、写两个 unit、`daemon-reload` 和 `enable --now`（`:1032`、`:1042`、`:1062`、`:1082`、`:1083`）仍在 `set -e` 下裸执行。任一步失败都不会进入 `recover_services`。这与脚本 `:985` 起“从停止到 enable --now，任何失败都先恢复”的注释不符。

隔离执行真实 `write_phase456` 生成脚本，仅替换远端特权工具：让二进制安装成功、第一次 unit 写入失败。调用轨迹确认两个服务已停止，脚本失败退出，后续没有任何恢复或启动调用。该实验是离线故障注入，不是 Linux systemd 实机部署。

修复要求：把完整服务切换纳入统一失败恢复；预先保存旧二进制、unit 与启用/运行状态，失败时恢复可运行的旧配置并报告恢复结果。对 unit 写入、reload、启动失败分别执行行为回归。原 K-R1 的同源同目标安装缺陷已经消除，本条是修复轮服务恢复范围的新阻断项。

### K2-R2 / P1：检查的是配置路径上的新文件，仍不能证明运行进程已升级

`scripts/deploy_linux.sh:1009`–`:1014` 吞掉停止服务的失败；`:1083` 的 `enable --now` 不会重启仍然 active 的服务。`:1130` 再读取 `systemctl show -p ExecStart`，`:1133` 执行该路径上的 `--version`。ExecStart 是 unit 的命令配置，并不是运行中进程所持有的可执行文件。Linux 上替换路径后，旧进程可以继续运行原 inode，磁盘路径却已经输出新版本。

隔离反例使 stop 返回失败、旧服务维持 active，配置路径与磁盘文件显示目标版本。真实生成的安装阶段和核验阶段均成功退出，并打印“unit runs”目标版本；全过程没有读取 MainPID 或进程实际映像。原 K-R2 要求的运行中版本核对因此仍未满足。

修复要求：停止失败应阻止切换或触发明确恢复；启动后从 MainPID 获取实际运行进程，核对其映像与目标二进制，或通过可归属到本次进程启动的版本证据校验。回归必须保留旧进程继续运行、磁盘路径已替换这一前置条件，不能只 mock ExecStart 字符串。

### K2-R3 / P1：非 root 预检仍漏掉其他用户的进程和私有身份目录

`scripts/deploy_linux.sh:426`–`:430` 的远端脚本以 SSH 用户执行，只有逐条带 `sudo -n` 的命令提权。phase1 的 `ss -ltnp/-lunp`（`:829`、`:844`）、身份目录探测（`:856`–`:858`），以及 phase456 的文件存在判断（`:960`、`:974`、`:982`）仍由非 root 用户执行；后续 `sudo cp` 不能补救前置判断返回 false。

在典型 Linux 权限下，非 root 的 `ss -p` 看不到另一个用户的 PID，无法由 `/proc/<pid>/cgroup` 找到旧 unit；私有目录内的 key/db 则会被当作不存在。修复轮确实增加了安装路径可写预检，但没有补齐原 K-R2 明确要求的既有进程和私有身份发现。离线执行 phase1 的权限模型确认所有 ss 探测均未走 sudo，并输出 `pid unknown`/`not-a-systemd-unit`。这会拒绝本可迁移的旧服务；在未发现已有身份的路径中，还可能遗漏备份或迁移。

修复要求：用已验证的 sudo 权限进行只读发现与存在性判断；无法确定既有占用、身份或数据库时，在任何切换前明确失败。增加非 root SSH 用户、其他用户持有端口、私有身份目录的行为验证。当前证据不应写成已验证 Linux 权限场景。

### K2-R4 / P2：STATUS 链接仍被按文件名替换为另一份交接

`scripts/check_repository.py:236` 对链接只保留 basename，`:272` 再拼接 `docs/<basename>`。目录、协议和主机全部丢失，因此所检查的文件不一定是 STATUS 实际链接的文件。

在干净导出树中，将 STATUS 的 K 链接全部指向 `archive/HANDOFF-BATCH-K-2026-11-14.zh-CN.md`，创建该独立文件并放入会触发既有矛盾规则的文本。完整检查器仍通过，报告核对的却是未链接的 `docs/HANDOFF-BATCH-K-2026-11-14.zh-CN.md`；直接检查真实链接目标则正确失败。把链接改为外部 URL、只保留同名文件尾部，也会被当成本地 K 交接接受。

修复要求：从 STATUS 所在目录解析链接实际目标，去掉 fragment 后规范化并校验路径；将真实目标与最新交接的规范路径比较。无法建立明确本地映射的外部 URL 不能满足当前交接锚定要求。增加同名异目录、外部同名 URL 的完整检查器回归。原 `f9582e5` 的未链接 K 反例确实已被修复，但 K-R6 的“实际链接目标”要求仍有可执行反例。

## 2. 已核对的有效修复及边界

预编译部署使用独立暂存路径，安装前检查可执行性、版本与哈希；ExecStart 的可执行路径已重写且保留参数。两个 Paramiko helper 采用阻塞 channel 与 stdout/stderr 双流排空；跳过 doctor 时 STUN 标签也随之调整。这些改善与第一节剩余缺口分别判断。

Windows runner 使用独立、单调的传输/校验截图计数，缺失时按状态命名报错，并在导出前检查目标文件；有效端点按应用的运行期环境变量优先、编译期值回退规则解析，校验后的同一配置传入应用和 CLI。直接导入 runner 的测试和真实走查产物支持这些修复。自建合成文件避免了依赖外部预置目录的问题。

Android 系统 SAF 证据包含实际 DocumentsUI 选择、发送完成与接收文件哈希一致；辅助 runner 是另一条注入选择结果的路径。宿主与模拟器、Windows 进程内 PNG、OS 截图、单元测试和物理双机验收分别记录，不相互替代。任务平台缺失 endpoint blob 的拒绝与旧 QEMU/探测竞态猜测也须分开；本轮没有重跑完整设备走查。

Rust 测试顺序调整让 owner 的 listening 先于 redeemer 启动，保留配对、撤销和后续发送的语义断言。API 读取的原失败日志、历史同用例失败、相同 Rust 代码的成功运行、旧候选重跑及新候选 CI 共同支持这项 harness 修复；它们不能证明所有可能的慢机超时均已消除。
