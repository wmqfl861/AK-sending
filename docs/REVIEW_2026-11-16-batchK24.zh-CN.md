## 0. 为什么本轮由复核方修复，而且要加守卫

部署脚本已经连续 23 轮 REJECTED。每一轮修掉上一轮的反例，下一轮又在“目录发现”环节找到新的边界输入：路径里的空格、换行、方括号、选项字样、符号链接、环境变量等。这些输入各不相同，但最终危害都落在同一处：**新服务加载了错误的 `registry.key`，或者在没有旧身份的地方新建了一个身份**。注册中心身份就是客户端钉扎的 RegistryId；按 [OPERATIONS §5](OPERATIONS.zh-CN.md#5-tls-身份密钥registrykey备份与轮换)，身份一旦变了，所有客户端都要重新钉扎，GUI 还要重新构建发布。

继续逐个补边界不会收敛。本轮的做法是：先修掉 K23 的五项，再在发现逻辑之外加一道与发现逻辑无关的终检，直接核对“新服务将要服务的身份”。不管发现环节选了哪个目录，只要身份不对就在停服前拒绝。

## 3. 修复（实现提交 `b8142cb`）

### K23-N1（P1）：find 完整路径被重复加 /home 前缀

- 原因：生产者 `find /home … -print0` 输出 `/home/otheruser`，消费者又拼成 `/home/$name/.ak-sending`，实际探测的是 `/home//home/otheruser/.ak-sending`。
- 修复：把记录协议固定为真实工具的输出格式。消费者只剥掉一次 `/home/` 前缀（引号内按字面匹配）；不是 `/home/<一级名字>` 形状的记录一律拒绝。改成两遍处理：先校验全部记录，再逐个探测，所以拒绝不会出现在部分候选已经输出之后，结果也不依赖文件系统的枚举顺序。
- 测试盲区：原来的 FIND_STUB 遇到 `/home` 就直接输出 basename，根本没有调用真实 find。现在桩对 `/home` **执行真实 find**，只把沙箱前缀映射回 `/home`；测试同时核对“真实工具输出的记录”恰好等于夹具建出的 `/home` 子目录，作为独立一致性检查。
- 回归测试：普通来源迁移（探测路径不含 `/home//home`）、嵌套诱饵不进候选（迁移的是普通来源的字节，诱饵不动）、两个普通来源触发多候选拒绝、三种协议外记录被拒绝。基线对照：`f578f39` 自身完整链对普通来源报告 none-found，在嵌套夹具下实际复制了诱饵的 key/db。

### K23-N2（P2）：/home 是符号链接时被当成空主机

- 原因：GNU find 默认 `-P`。起点是目录符号链接时，它不下降、零输出，退出码仍是 0。
- 修复：改用 `find -H /home …`，只跟随命令行起点，与改动前 `ls -1 /home` 列出链接目标的语义一致；`/home` 下面的条目本身仍不跟随。`-H` 遇到悬空链接同样零输出、退出码 0，所以生产者之前先加一道 `sudo -n test -d /home`，`/home` 不是目录（或悬空链接）就拒绝。
- 回归测试：真实目录符号链接下迁移普通来源；悬空链接和普通文件两种情况都在生产者运行前拒绝。基线对照：`f578f39` 在链接夹具下真实 find 零输出，读成全新主机。

### K23-N3（P2）：诊断路径放在 case 模式里

- 修复：把期望的完整诊断 `ls: cannot access '<路径>': No such file or directory` 先存进变量，再用 `[ "$pe_out" = "$pe_enoent" ]` 做字面比较。`[ = ]` 是字符串相等，不做模式匹配。
- 回归测试：只有空目录、名为 `spare[1]` 的 home 继续按全新安装处理，与普通名 `spare1` 一致。helper 合同注入四种情况：方括号请求遇到另一路径的 ENOENT → 不可判定；星号请求遇到另一路径的 ENOENT → 不可判定；同路径方括号 ENOENT → 不存在；Permission denied → 不可判定。基线对照：`f578f39` 对方括号空 home 拒绝 phase1。

### K23-N4（P2，7e8bfb2 起的既有缺口）：监听参数按子串比较

- 修复：新增 `bound_listen_arg`，规则与 `bound_db_arg` / `bound_id_dir` 相同：完整 token，等号形式取本 token 的后缀，空格形式取下一个 token，遍历时关闭 glob。`--port` / `--bind` 先过 CLI 语法门（悬空、空格形式的值像选项、等号后为空、重复绑定，任一情况返回 rc 3 并引用 CLI 自己的报错），再按有效值比较。
- 为什么字符串相等就够：CLI 由（port, bind）两个值确定性地算出监听地址（完整 `ip:port` 形式的 `--bind` 优先于 `--port`），所以两组原始值相同，监听地址必然相同。最坏情况只是等价写法（例如 `07200`）被保守地判为不同而拒绝。
- 回归测试：helper 合同覆盖 9 种情况，包括 K23 的两组遮蔽输入（现在判为不同）、同形选项样路径、等号与空格写法、缺省与显式缺省值，以及四类语法错误。phase1 全链测试：port 与 bind 两组遮蔽夹具都以 materially disagrees 拒绝，没有任何 stop。基线对照：`f578f39` 的 helper 对遮蔽输入返回一致。

### K23-N5（P2，CI 红灯原因）：NTFS 名称映射没有区分平台

- 修复：`_ntfs_backing()` 只在原生 Windows Python（`os.name == "nt"`）上映射。映射范围补全为 MSYS 实际使用的整套私用区规则（控制字符 0x01–0x1f 以及 `"*:<>?|`）；POSIX 主机按 Bash 创建的原字节读取。
- 新增平台单测。原 LF 回归测试在 Linux 本机已通过；CI 结果见 §7。

### 用 K23 复核方自己的夹具复测

把 K23 §8 的三段脚本改为读取工作树。只改了夹具胶水：K23 自写的 find 桩写死了 `args[0]=/home`，改成识别 `-H`；没有改动任何语义。在修复后的代码上重跑，结果全部按预期翻转：

- 普通来源、链接起点、嵌套诱饵都迁移普通来源的字节；两个普通来源被拒绝；LF/CR 整名拒绝和生产者失败拒绝保持不变。
- 监听遮蔽两组在停服前拒绝，普通对照不变。
- 三个错路径诊断探针都返回不可判定；方括号空 home 继续。

## 4. 收敛措施：注册中心身份连续性守卫

**新增只读子命令 `ak-cli [--id-dir D] registry-id`**

- 读取已有的 `D/registry.key`，打印一行 64 位小写 hex。它与 `registry-server` 共用同一个加载器（新增的 `DeviceKeyPair::load_existing`，校验规则与 `load_or_create` 相同，只是不创建）和同一个格式化函数（`registry_pin`）。
- 不创建目录，不创建密钥，不开端口，不碰数据库；密钥缺失或损坏时报错退出。
- 测试：ak-identity 单测；ak-cli 单测（两种参数位置都能解析、不创建目录、输出与服务端格式化一致）；跨进程集成测试，先启动真实 `registry-server` 读取它打印的 pin，再用 `registry-id` 读同一目录，两者逐字相等，缺失时失败且不留下任何目录。

**部署脚本新增选项与三道检查**

- 新选项 `--expect-pin <hex>`，默认是仓库记载的生产 pin；新选项 `--new-identity` 表示有意使用全新身份。两者互斥，格式在参数解析阶段就校验。
- 检查一，停服前：用新二进制的 `registry-id` 推导新 unit 将要加载的身份。如果迁移会把来源的 key 复制进身份目录，就推导来源那份；否则推导身份目录自己那份。身份不一致、身份缺失（会新建身份）、无法推导、身份目录不是绝对路径，这几种情况都以 exit 5 拒绝，此时没有停掉任何服务，零停机。
- 检查二，最终迁移之后、换二进制和写 unit 之前：在受保护的切换窗口里，对实际要被加载的那份文件重新推导一次。不一致就走统一恢复，旧二进制、旧 unit 和运行中的镜像都恢复原样。
- 检查三，第 7 阶段：如果运行中服务打印的 pin 与期望不同，以 exit 6 失败，而且不会把错误的 pin 导出给客户端脚本使用。
- 模式校验：`--new-identity` 模式下如果发现会服务一个已存在的身份，同样拒绝，并在提示里给出 `--expect-pin <该 pin>` 的重跑方式。

**效果**

不论 occupant、environ、cmdline、目录枚举哪条发现路径出错，只要结果是选错来源、或者让服务新建身份，都会在停服前被拒绝。测试已用错误来源（诱饵）和停服过程中来源被改写两种情况演示了这一点。

**边界**

- 守卫只管身份，不管数据库连续性。数据库仍由原有的迁移后 cmp 校验和备份负责。
- OPERATIONS §3 记载的生产 pin 尚未在服务器上核实。如果它与现网不符，脚本会在停服前拒绝，并打印出它将要服务的 pin；所有者确认后用 `--expect-pin` 重跑即可。这正是守卫要求的“有意识的确认”。
- 守卫只在离线模型和真实 CLI 二进制上验证过，没有在原生 systemd 上跑过。

## 5. 部署脚本的验收口径（从本轮起）

以下情况**阻断**合入：

1. 服务的身份与期望不同，或在没有确认的情况下新建了身份（即守卫被绕过）。
2. 停服后服务没有恢复，又没有报告 RECOVERY INCOMPLETE；或者某一步失败了，脚本却报告成功。
3. 来源的身份或数据库被改写、删除或移动。
4. 违反红线：ADR-001、生产访问、密钥入库。
5. 被审 tip 的 CI 有红灯。

以下情况**不阻断**，作为 P3 记入 BACKLOG，择机处理：

- 发现环节遇到特殊输入，结果是停服前保守拒绝、主机状态没有任何变化。例如引号或控制字符的名字、等价写法 `--port 07200`、白名单外的路径字节。
- 日志或提示的措辞问题。

真机验证仍属于所有者的 E6：先跑 `--check-only`，再带 `--expect-pin` 正式部署。
