## 2. 新发现

### O-N1（P1，既有缺陷）：单个大文件的整文件处理期间，发送端空闲超时

**机制**

- N-N1 让接收端在准备与校验两段里“在文件之间”定时发活动信号，但单个文件自身的处理是一整段阻塞过程，中途不发帧：
  - 校验阶段的 `finish()`：对整个文件做摘要校验，再 `sync_all` 落盘；
  - 准备阶段：续传时逐块重新哈希已有 part 文件的已验证前缀，或在重试时重新哈希已提交的最终文件。
- 发送端等每一帧都受空闲时限约束（默认 30 秒）。这一段一旦长于 30 秒，发送端就放弃，而接收端照样把文件提交完、报告成功。
- 普通磁盘上，这一段的长度大致是“文件大小 ÷ 读盘速度”再加刷盘时间：机械硬盘或 USB 移动硬盘上几 GB 的文件就会超过 30 秒，SATA 固态硬盘上是十几 GB。
- 在单线程测试运行时里，这段阻塞还会停住 QUIC 自己的计时器；长过 60 秒，连接直接断开，报 connection lost。

**证据**（数字见 O 交接 §9）

- 复核方的工作区（磁盘很快）：12 GiB 文件、两端时限 3 秒、多线程运行时，校验阶段长于时限，发送端 `IdleTimeout(3s)`，接收端成功；先断一次、留下大半个 part 文件再续传，结果相同。
- 新增的 release 测试 `large_file_passes_keep_the_sender_waiting`（4 GiB 文件，其中 3 GiB 已在 part 文件里，两端时限 300 ms，多线程运行时）：去掉修复时以 `IdleTimeout(300ms)` 失败，加上后通过。

**修复**（`f9384b9`）

- 不小于 64 MiB 的文件，其整文件处理交给 tokio 的阻塞线程池执行；接收任务本身照旧按活动间隔发信号：准备阶段发空的 `more = true` ResumeRequest 分片，校验阶段向带 `CAP_PAUSE_RESUME` 的发送端发无操作的 `Control::Resume`。更小的文件仍在文件之间检查间隔，即使磁盘只有 100 MB/s，它们的单次处理也远短于活动间隔。
- 接收任务不再被阻塞，传输层（包括 QUIC 的计时器）照常运行，单线程运行时里的连接断开也随之消失。
- 某次活动信号发送失败时，正在进行的处理照样做完、结果照常返回，由下一帧常规发送报告连接已断并走原有的清理路径，所以不会留下多余的 part 文件。
- 没有新增消息类型，线缆布局不变；PROTOCOL 的接收端活动信号一段已更新。

**测试**

- `offloaded_pass_keeps_signalling_until_it_finishes`：真实的环回 QUIC 流上，650 ms 的阻塞处理、100 ms 的间隔，至少收到 4 个信号；没有信号帧时什么也不发，处理照样完成。
- `large_file_passes_keep_the_sender_waiting`：release 才跑（同 5 GiB 测试），覆盖准备与校验两段。

### O-N2（P2，性能）：块阶段检查点的写入量随文件数平方增长

**机制**

- 检查点每次保存都把整份记录重写一遍并落盘，记录的大小与文件数成正比。
- 块阶段里，发送端每发完一个文件就保存一次，接收端每收到 16 个块保存一次。全是小文件时，保存次数也与文件数成正比，写入总量于是随文件数平方增长。
- 两项里发送端是主要部分：它的保存频率是接收端的 16 倍。复核方起初只改了接收端，65,537 文件项的块阶段只缩短了一小部分；再改发送端，块阶段才降到几秒。
- O2 的 Windows 数据也对得上：块阶段每个文件的平均耗时随文件数明显增长（数字见 O 交接 §9）。

**修复**（`0d4d88f`）

- 两端的检查点在块阶段都至多每秒写盘一次：
  - 发送端每个文件的进度照旧立即记入内存中的记录；
  - 接收端的进度（`BytesAcked`）照旧每第 16 个块报告一次。
- 接收端在校验阶段开始前仍完整保存一次（N-N1 起如此）；两端任务结束时的“完成”或“失败”状态照旧立即保存。
- 两端的续传都不依赖这些中途保存：接收端重新哈希 part 文件，发送端按接收端的 ResumeRequest 续传。正确性因此不受影响。
- PROTOCOL 的持久边界说明与 engine 模块文档已同步。
- 测试 `chunk_checkpoint_saves_at_most_once_per_interval` 覆盖接收端的新节拍：多文件突发不再写盘；间隔较长的大块仍是每 16 个块写一次。

**效果**

- 复核方工作区上，65,537 文件项的块阶段从数百秒降到几秒，整项从六七分钟降到二十多秒（前后数字见 O 交接 §9）。
- Windows 上的效果由批次 P 测量。

### O-N4（P2，既有缺陷）：注册服务器先宣告就绪后监听，集成测试选端口有竞态

**现象**

- 第一次快进合入后，main 的 push CI 里 Windows 任务失败一项：`t03_ipv6_loopback` 的 `probe_answered_non_quic_candidate_falls_back_to_the_real_receiver`。测试 10 秒内没等到接收端打印 `receiver bound`，接收端的 stdout 一行也没有。
- 这不像整机变慢：同一个测试二进制里稍后启动的其他接收端几秒内就绪；同一提交此前在 dev 分支上的 CI 全部通过；CI 历史里这项测试没有失败过。只重跑失败任务的结果见 O 交接 §9。
- 测试的超时报错只带接收端的 stdout。接收端要先连上注册服务器才会打印第一行 stdout，连不上时原因只写在 stderr，而这次 stderr 没有留下。所以这次失败的直接原因没能从输出里查实。

**机制**（复核方逐项复现，证据见 O 交接 §9）

- `ak-cli registry-server` 在绑定监听端口之前，就打印了两行就绪输出（`v2 pairing registry on tls …` 与 `registry id …`）。绑定在另一个任务里进行，失败时只有那个任务结束；主任务只等 Ctrl-C，所以进程照样运行，也不报错，收到 Ctrl-C 才报出绑定错误。打不开数据库时也是这样。
- 五个起注册服务器的集成测试文件都是同一种做法：先在 127.0.0.1 上绑一个临时端口，读出端口号后释放，再让注册服务器子进程绑定 `0.0.0.0` 的同一端口。两步之间，这个端口可能被别的连接占用，并行测试里正有很多进程在建连接。端口一旦被占，注册服务器绑定失败，却照常打印就绪行；测试见到这行就启动接收端，接收端连不上，把原因写到 stderr 后退出。这正是这次的现象。
- 另一种可能也来自同一处缺陷：注册服务器打印就绪行之后、真正绑定之前，有一段极短的空隙，接收端恰好在这时去连。
- 生产上的影响：部署脚本第 7 步只核对端口上有进程在监听。端口若被别的进程占着，旧行为下新服务显示为 active 却不在服务，这一步也查不出来。

**修复**（`2e57683`）

- `registry-server` 先绑定端口、再打开数据库，两步都成功后才打印就绪行，打印的是实际绑定的地址，所以 `--port 0` 也可用。任一步失败，命令直接退出，错误里写明地址或数据库路径。服务循环若自行结束，命令也带着错误退出，不再空等 Ctrl-C。
- 为此 ak-signal 新增 `bind_v2`；`run_v2` 改为先调用它，行为不变。
- 五个集成测试文件改用 `--port 0`，从就绪行读出端口，不再先探端口。
- 这些文件里等待子进程输出超时时，报错带上该进程的 stderr，同类失败以后能直接看到原因。
- README 的 registry-server 说明已同步。

**测试**

- 新增单元测试 `registry_server_fails_fast_when_its_port_is_taken`：端口被占时，命令在时限内返回错误，错误里有这个地址。
- 五个集成测试文件全部通过；它们现在都从就绪行读端口。

**边界**

- 这次 CI 失败的直接原因仍是推断。修复去掉了上面两类原因，并让同类失败留下 stderr；若 Windows CI 上再出现，按新的报错查。
