### Q-N2（P2，性能）：校验阶段逐个文件串行处理

**现象**（P 复核登记的 BACKLOG 项）

- 接收端在校验阶段逐个文件做整文件摘要、落盘、建立最终名，一个接一个。O-N2 让块阶段变快之后，Windows 上 65,537 文件项的校验阶段约占整项耗时的七成（P 交接 §9）。
- 每个文件的这一步主要在等文件系统：打开、读、落盘、建立最终名。Windows 上每个文件的这部分开销是复核方 Linux 工作区的二十多倍（换算见 Q 交接 §9）。

**改动**（`2a31939`）

- 校验阶段每个文件的 finish() 都放到阻塞线程池上执行，同时至多 8 个（`VERIFY_PARALLEL_FILES`）；不小于 64 MiB 的文件同一时间至多一个，避免几个多 GB 的文件同时抢磁盘。
- 每个文件内部的顺序不变：整文件摘要通过、数据落盘之后才建立最终文件名。“改名之前数据必须已经落盘”没有放松。
- 接收任务在等待期间按原来的间隔发活动信号；大文件原来走 `offload_with_liveness`，现在由同一个循环处理。进度事件按完成的先后报告，界面与 CLI 都按文件序号处理，不受影响。
- 某个文件失败后不再开始新的文件，已开始的全部返回之后才报错：接收函数返回时，不会还有线程在目标目录里写。
- 检查点的定时保存与重试语义不变：重试时，已提交的文件由存储层对最终文件做整文件摘要比对后跳过。
- 线缆格式不变；PROTOCOL 的接收端活动信号一段与 engine 的模块文档已同步。

**验证**

- 新增测试 `verify_failure_waits_for_running_passes_and_a_retry_completes`：24 个文件，进入校验时改坏其中一个文件的 part 文件。断言接收端报 HASH_MISMATCH，返回之后目标目录不再变化，每个文件要么已提交且内容正确，要么还是 part 文件；同一任务再跑一次，跳过已提交的文件，重新取回改坏的那个，最后没有多余的副本。这些性质旧的串行循环本来就满足，测试在旧循环上也通过；它守的是并行之后不能丢掉这些性质。
- 原有的 `slow_verify_phase_keeps_the_sender_waiting` 通过。
- release 深测（复核方工作区）：大文件测试与 5 GiB 项通过。反证：临时去掉新循环里的活动信号（不入库），大文件测试失败，发送端在进入校验 300 ms 后报 IdleTimeout。
- 规模测试的校验阶段，复核方工作区上改动前后各跑两次：65,537 文件项与 20,000 文件项都缩短到约一半。
- CI 的 Linux 深测：改动后的三次手动运行里，两个规模测试的校验阶段约为改动前的三分之一到一半。
- CI 的 Windows 深测：65,537 文件项的校验阶段改动前一次、改动后三次，改动后三次都比改动前短，但三次之间相差近一倍；20,000 文件项改动后三次有长有短。windows-latest 每次分到的机器性能不同，这几次运行分不出改动的效果（数字见 Q 交接 §9）。Windows 上的效果以批次 R 在同一台本地机器上与 P2 的对照为准。

**Windows 上每个文件的开销**

- 复核方新增了只在 release 下运行的基准测试 `bench_commit_cost`（`fcc79c3`、`29532ee`）：在 2,000 个一字节文件上分别计时校验阶段的各步，单线程与 8 线程各一遍，只打印每步的平均值，不打印路径。Linux 深测本来就跑全部 ignored 测试，Windows 深测任务也加上了这一步。
- windows-latest 上的结果（Q 交接 §9；共同的各项两次运行同一量级，最后两项对照只在第二次）：
  - 重新打开一个已经关闭的文件并落盘，每个约 0.3 ms；在同一个句柄上创建、写入、落盘，每个约 5 ms，8 线程也不更快；写穿（FILE_FLAG_WRITE_THROUGH）更慢；
  - 建立最终名（hard_link 加删除 part 名）、改名、改时间戳，每个都在 0.6 ms 以内；
  - 按 finish() 现在的顺序逐个文件“落盘、建立最终名”，每个文件约 3.9 ms，8 线程也一样；同样的工作分两遍做，先把全部文件落盘、再逐个建立最终名，每个文件约 0.9 ms，8 线程约 0.5 ms。两种做法里，每个文件都是先落盘、后出现最终名。
- Linux 上两种顺序只差一两成；那里并行的落盘可以合并（8 线程时每个文件的落盘便宜好几倍），这正是 Q-N2 在 Linux 上大幅见效的原因。
- 推断（没有在文件系统内部验证）：NTFS 落盘时要把整个卷共用的日志写到盘上。一个文件落盘之后紧接着建立最终名，日志里又多了记录，下一个文件落盘就得再写一次日志；交替进行时每个文件都付一次，也无法靠并行重叠。先把一批文件都落盘，日志只写一次。
- 下一步（登记在 BACKLOG）：校验阶段按批处理，先把一批文件落盘，再建立这一批的最终名。每个文件仍是先落盘、后出现最终名；finish() 要拆成两步，并在建立最终名之前重新核对 part 文件的身份，不让两步之间的间隔变成可乘之机。复核方准备在批次 R 的本地结果（R3）出来之后做。
- 本地 Windows 的确认交给批次 R（R1、R2、R3）。
