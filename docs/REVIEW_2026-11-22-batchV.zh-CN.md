## 2. 复核方登记的新问题

### V-N1（P3，记录）证据表被 shell 转义破坏

V 交接 §8 的打包冒烟一行里，Windows 路径 `flutter\release\ak_ffi.dll` 的 `\r`、`\a` 被 shell 解释成回车与响铃符：这一行被拆成两段，后半段落到表格之外，另有三处路径丢了字符。

复核方在 `0cc9baa`：

- 按上下文恢复了这一行与三处路径；
- `check_repository.py` 新增规则：Markdown 里出现 TAB、LF 以外的任何 C0 控制字符（包括 CR）都报错，并附三条单元测试。

给执行方的做法：往文档里写含反斜杠的内容时，用编辑器或带引号的 heredoc（`<<'EOF'`），不要用 `echo -e` 或不带引号的 `printf`。

### V-N2（P1，产品）长时间后台后的僵尸连接行

V2-b：连接在后台期间已经断开，宿主早已报错；应用回到前台后，连接行一直显示在列表里，没有错误、没有结束标记，直到 30 分钟观察窗结束。V2-d 是同样的中断，界面却报出了失败。用户在 V2-b 的情形下无法知道传输已经死了，也不会去重发。

要查清的是两条路径为什么不同：引擎是否对每个关闭的 QUIC 连接都发出终止事件；应用回前台时是否会与引擎核对连接状态。修复要求：任何一个连接断开后，界面最迟在回到前台后的几秒内显示失败，并给出“重新发送”。由 W1 处理。

### V-N3（P2，产品）回前台后窗口全黑

V2-b 回前台后应用窗口全黑，进程存活，runner 仍在输出进度。只出现过一次，而且是 debug 构建、模拟器。先用 profile 构建按 V2-b 的步骤复现；复现不了，记录后关闭；复现了再修。由 W2 处理。

### V-N4（P2，产品）错误显示异常原文，文案与原因不符

V2-d 界面显示 `发送失败：AkFfiException(AK_FAILED 2): transfer failed after connecting via …: stream failed: connection lost`，下面又显示“配对已闲置过久，请重新配对”。前者是给开发者看的原文，后者与真实原因（连接中断）不符。由 W3 处理，文案规范见 [审核 §4.3、§4.5](AUDIT_2026-11-22.zh-CN.md#43-关键流程)。

### V-N5（P3）Android 冷启动慢

V4 里 debug 构建在模拟器上冷启动到首帧很慢（数字见 V 交接 §8）。debug 与模拟器都会放大启动时间，先用 profile 构建实测。由 W6 处理。

### V-N6（P3）打包卫生

- Windows 包运行后在 `%TEMP%` 留下 `ak-stage.log`，删除程序目录后仍在；
- 发布包可以从带未提交改动的工作区构建（版本行带 `-dirty`）。

建议：启动阶段日志写到应用自己的数据目录（卸载说明里列出这个目录）；`package_windows.ps1` 发现工作区不干净时默认失败，加 `-AllowDirty` 显式放行，并把放行写进包内清单。由 W5 处理。
