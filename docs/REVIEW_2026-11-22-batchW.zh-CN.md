## 2. 复核方登记的新问题

### W-N1（P1，产品，复核方已还原）加入时不选方向，跨设备必然失败

**现象。** W7.1 的第 1 项去掉了加入面板的方向选择，`joinCode` 不传 `role`。对端若创建的是“我要接收”码，加入方（App）不传 role，两端都成了接收方；创建方的方向校验在服务器提交之前拒绝同向配对，加入方只看到统一的“配对目标不可用”，码仍可兑换，重试也没有用。创建方是发送方的码恰好能通，因为缺省的接收方与之互补。

**根因。** 契约写的“加入方得对侧角色”只在同一个引擎里成立：`run_join` 的角色顺序是 join spec 的 `role` → 本引擎码缓存里的创建方角色取对侧 → 缺省 receiver。跨设备时创建方的角色不在码里，缓存里也没有这个码，所以落到缺省。`ak-ffi/src/task.rs` 的模块说明、Dart `ffi_simple_transfer_service.dart` 的注释、`ak-session` 配对模块的说明都写明加入方向是“调用方（用户意图）声明”的。这一误读始于复核方自己的审核 AUD-05 与 W 交接 §4.7（交接里还特意写了“若引擎在不传 role 时有任何不同行为，先停下”；执行方的 §8 只引用了契约那一句，看不到对引擎跨设备行为的核对）。

**为什么所有测试都绿。**

- Rust 的任务测试大多在同进程里用同一个或成对的引擎，同引擎缓存会镜像对侧角色；跨引擎的那几条测试都显式传了 `role`；
- 假服务 `simple_transfer_fake.dart` 在 `role == null` 时取“创建方的对侧”，替身比真实引擎宽容（W-N7）；
- 走查用的是“App 建发送码 + 宿主 CLI 接收”，恰好走在能通的那一边。

**处理。** 复核方在 `da70e5f` 还原加入面板的方向选择，保留 W7.2 的自动弹选择与按实际角色提示的成功卡；还原了被改的五处测试，把 `w7_interaction_test` 里钉死“不传 role”的那一条改成钉住“必须选方向、且把声明的方向传下去”；`ffi-v2.md` 把那句话改成不会再被误读的写法；审核 AUD-05 加了勘误。只经 CI 验证。批次 X 的 X1 补：双引擎 Rust 测试钉住“跨设备缺省为 receiver、同向被拒”，假服务缺省与真实引擎对齐，并做两个新方向的真机走查；去掉重复选择的正确办法见本文 §4。

### W-N2（P2，产品）看门狗覆盖校验阶段

`_checkStalledTransfers` 对进度阶段 2（传输中）和 3（校验中）都生效。接收端在校验阶段只在每个文件校验完成时才发进度，一个超大文件在慢存储上校验超过 150 秒，行会被误标为 `conn_lost`——界面先报失败，真实传输随后可能成功。W1 的 Dart 测试覆盖了传输中、持续进度、等待同意三种情形，没有校验阶段。修法：校验阶段不参与看门狗，或预算按字节数放大；补测试。

### W-N3（P3，产品文案）兜底把本地错误也归为连接中断

`post_connect_verdict` 的兜底（其余一切）在发送端读不了源文件、源文件在传输中变化时也上报 `conn_lost`，界面写“连接断开了”，真实原因在本地，只在“详情”里能看到。连接随之结束，行为本身可以接受，问题在文案。建议文案保持中性（“连接断开了，或发送过程中出了问题”），原文仍在详情；与 W-N8 一并改。

### W-N4（P3，产品文案）`-2` 在所有场景都映射为“这个码用不了”

`classifyTransferError` 把 `AK_ERR_INVALID`（-2）一律当作任务码问题。发送的参数错误或启动配置错误也会被说成“这个码用不了”。限定在加入场景，其余场景走词表与兜底。

### W-N5（P3，工程）CLI 仍是单属性匹配

`task_cli.rs` 里，接收侧只按消息识别 TASK-CLOSE，发送侧只按错误码识别 DECLINED，与 FFI 的双匹配不一致；执行方在裁决追改时有意没动，交复核方决定。决定：改。把 `post_connect_verdict` 的两个判定下沉到 `ak-engine`，FFI 与 CLI 共用，测试随之搬过去。

### W-N6（P3，记录）§8 的路径再次被转义吞掉；最终 CI 行陈旧

W 交接 §8 里启动日志的路径（身份目录下的 logs 目录，以及系统临时目录）共三处被吞掉了文件名前的反斜杠和首字母 a，读上去像另一个文件名。这次被丢弃的是响铃符本身，没有留下控制字符，V-N1 的检查抓不到。另外“W 批次最终 CI”一行引用的是中间提交 `18b1ecc`，最终提交是 `f581ebd`。复核方在 `38a6f46` 恢复路径，给 `check_repository.py` 加“路径分隔符被吃掉”的检查（路径占位符后直接接字母，或启动日志的文件名缺了首字母）与两条单元测试，并在 §9 记最终提交的 CI。

### W-N7（P3，测试）假服务比真实引擎宽容

见 W-N1。批次 X 的 X1：假服务在不传 `role` 时缺省为接收，依赖旧缺省的测试改成显式传 role；再加一条双引擎 Rust 测试钉住真实引擎的缺省。凡是“靠契约一句话”推出的界面行为，先找到实现它的那行代码。

### W-N8（P3，产品文案）连接中断之后没说要重新配对

`conn_lost` 之后配对已经结束，必须先重新配对才能再发；但发送场景的状态行与失败卡写的是“重新发送，会从断点续传”。走查里失败之后的第二段用的是新任务码（V 交接 §8 的 V2-b 第二段，W 的两轮同型），也就是重新配对。发送场景改成“请重新配对后再发送，会从断点续传”，接收场景与配对场景的文案已经是对的。

## 4. “免选方向”的正确做法

加入方的方向在现协议下只能由调用方声明，所以加入面板里那一步不能靠删掉来解决。审核 §4.3 其实已经给出了做法：首页两个主入口“发送文件”“接收文件”，**方向由用户一开始点的按钮决定，只声明一次**——

| 入口 | 主路径 | 次要入口 |
|---|---|---|
| 发送文件 | 先选文件，再生成码（创建方为发送方），对方加入后自动开始发送 | “对方已经给了你一个码？输入对方的码”（加入方为发送方，方向已知） |
| 接收文件 | 输入对方的码（加入方为接收方，方向已知） | “想让对方输入你的码？生成接收码”（创建方为接收方） |

四个组合里，方向都来自第一次点击，加入面板与生成码前都不再问。这是批次 X 的 X4。W7.1 的初衷（少一步、不选错）因此得以实现，同时不依赖引擎推断。

## 5. 过程上的观察

- **测试替身要和真实引擎同语义。** 这次所有 Flutter 与 Rust 测试都绿，缺陷却在真实跨设备路径上。凡是界面行为依赖引擎语义的地方，假服务要么与真实引擎一致，要么在 Rust 一侧有钉住该语义的测试（X1）。
- **复核方的交接也会写错。** 审核与交接里关于契约的说法，执行方应当去代码里核对，核对不了就停下来写在 §8。这条要求写在了 W7.1 里，§8 里却看不到对应的核对；可见要求“不同行为就停下”不如要求“先找到实现它的那行代码”。
- **证据放在 `/tmp`。** W 的走查原始输出放在执行方本机的 `/tmp`，复核方看不到，只能依赖 §8 里原样贴的关键行。按 AGENTS.md 不把真实路径与诊断入库是对的；做法保持，但结论所依赖的关键行必须原样贴进 §8。
- **外部裁决。** 执行方应所有者要求请外部 agent（codex）复核，追改的三处都成立。其对 O-1、O-3、O-6 的“预审”不是所有者的决定，O-1 至 O-7 仍待所有者。
