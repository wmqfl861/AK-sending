### W-N1（P1，产品）加入时不选方向，跨设备必然失败

**现象。** W7.1 的第 1 项去掉了加入面板的方向选择，`joinCode` 不传 `role`。对端若创建的是“我要接收”码，两端都成了接收方，配对被拒；加入方看到的是“这个码用不了”，重试也没有用。

**依据。**

- 〔代码〕`run_join` 的角色顺序是：join spec 的 `role` → 本引擎码缓存里创建方角色取对侧 → 缺省 receiver。跨设备时缓存里没有这个码，落到缺省。创建方的方向只在配对提交时才到达加入方，所以只有创建方能在提交前做方向校验（`veto_task_offer`），同向即拒绝，且不消耗这个码的兑换次数。
- 〔CI〕这不只是阅读结论：仓库里从 2026-11-07 起就有一条双引擎测试 `production_owner_loop_refuses_same_direction_joins_before_commit`，第二阶段正是“不传 role 的跨引擎加入遇到 receiver 码被拒，显式声明 sender 后同一个码仍能配对”，它在每次 CI 里都通过。
- 〔代码〕被拒时加入方拿到的是统一的 `unknown task code (or expired, revoked, owner offline)`，界面映射成“这个码用不了”。

**为什么自动化测试没有拦住。** Rust 一侧其实拦着（上面那条测试），但界面改动没有和它对上：Dart 假服务在不传 role 时取“创建方的对侧”（W-N7），所以全部 Flutter 测试都绿；走查用的是“App 建发送码、宿主 CLI 接收”，恰好是能通的方向；而驱动“App 加入一个接收码并发送”的 K1 脚本没有重跑（W-N12）。

**根因在复核方。** W 交接 §4.7 和审核 AUD-05 把契约里“加入方得对侧角色”读成了跨设备也成立。

**现状与修复建议。** 复核方在 `da70e5f` 把选择面板还原了（越权，只经 CI，见 §3）。批次 X：X1 用 K1 走查做设备验证并让假服务与引擎一致；X4 做真正的解法（§4）。

### W-N2（P2，产品）看门狗在校验阶段误报

**依据**〔代码〕。接收端收完数据后，要把每个文件整个重读一遍算摘要再提交（`finish()`），这期间只在每个文件完成时发一条进度；发送端此时在等最终确认，同样没有进度。线路上有保活帧，所以引擎自己不会超时，但 Dart 的看门狗只数进度行，传输中和校验中两个阶段都在它的范围内，150 秒没有进度就把这一行标成 `conn_lost`。单个文件的重读时间与大小成正比：按每秒 100 MB 估算，约 15 GB 的文件就会超过预算（估算，未实测；内置存储更快，门槛相应更高）。结果是界面先报“传输中断”，真实传输随后成功，两端都会发生。W1 的 Dart 测试没有覆盖校验阶段。

**修复建议。** 预算到期时不要直接标记，先用 `ak_task_list` 问引擎：引擎仍认为连接在，就重新计时（最多在界面上提示“长时间没有进展”）；引擎已不认识这条连接才标 `conn_lost`。引擎自己会发现死连接并发 `conn_lost`，看门狗只该是兜底。退一步的做法是让校验阶段不参与看门狗。补测试：校验阶段超过预算不被标记，传输阶段的死连接仍被标记。

### W-N3（P3，文案）`conn_lost` 的范围比“连接中断”宽

〔代码〕`post_connect_verdict` 的兜底包含三类：真正的链路中断；发送端本地错误（读不了源文件、源文件在传输中变化）；接收端用错误帧报告的问题（空间不足、无法写入）。后两类连接行也显示“连接断开了”。连接随之结束这一点可以接受，问题在文案。建议连接行的文案保持中性（“连接已结束”），具体原因交给 op 的错误卡；与 W-N8、W-N10 一起改。

### W-N4（P3，文案）状态码 -2 的映射不分场景

〔代码〕`classifyTransferError` 把 -2 一律当作任务码问题。发送的参数错误或启动配置错误也会被说成“这个码用不了”。限定在加入场景，其余场景走词表与兜底。

### W-N5（P3，工程）CLI 仍是单属性匹配

〔代码〕`task_cli.rs` 发送侧只按错误码识别 DECLINED，接收侧只按消息识别 TASK-CLOSE，与 FFI 发送侧的双匹配不一致。（FFI 接收侧 `runs.rs` 也只按消息，但那一支与兜底分支的处理相同，没有行为差别。）建议把这两个判定下沉到 `ak-engine`，FFI 与 CLI 共用。

### W-N6（P3，记录）§8 的路径被转义吞掉；最终提交没有 CI 记录

W 交接 §8 里启动日志的路径有三处丢了分隔符和文件名的首字母。复核方在 `38a6f46` 按代码里的文件名补了回去——这是推断，需要执行方确认原意。另外 §8 标着“W 批次最终 CI”的那一行引用的是 `18b1ecc`，而最终提交是 `f581ebd`，它的 CI 没有记在 §8；复核方把它记在了 §9，§8 那一行没有再动。

### W-N7（P3，测试）假服务比真实引擎宽容

〔代码〕`simple_transfer_fake.dart` 有两处比引擎宽：不传 role 时取创建方的对侧（引擎是缺省 receiver）；双方同向时照样配对成功（引擎会拒绝）。修复建议：两处都与引擎对齐，同向时返回与引擎相同的失败文本；依赖旧行为的测试改成显式传 role。

### W-N8（P3，文案）连接结束后的文案不分原因

〔代码〕详情页对“非闲置、非完成”的结束一律显示“连接已中断，重新发送会从断点续传”，对方主动断开、自己断开也是这句；失败卡在发送场景写“重新发送，会从断点续传”。而连接结束后配对已经失效，必须先重新配对。建议按断开原因选文案：对方断开——“对方已断开连接”；连接中断——“连接中断了。请重新配对后再发送，会从断点续传”；自己断开不必提示续传。

### W-N9（P2，文案）“这个码用不了”掩盖了两种常见原因

〔代码〕引擎的统一拒绝文本涵盖：码不存在、过期、已撤销、**对方不在线**，以及**双方方向相同**。界面只说“码可能输错了，或已过期/已被使用……请让对方重新生成，再输入新的码”。方向选反的人照做只会再失败一次；对方的应用被切到后台、无法应答时，按代码推断也是这句。引擎出于防枚举不区分原因，所以文案必须把可能性列全。修复建议：加入场景的原因与建议补上“对方需要保持应用打开并停留在前台”和“请确认两人没有选同一个方向（一方发送、一方接收）”。X4 之后主路径不会再选反，但次要入口仍可能，文案仍然需要。

### W-N10（P2，文案）对方空间不足时发送方看不懂

〔代码〕接收方空间不足时回给发送方的文本是 `peer sent error STORAGE_FULL: insufficient free space at destination`（传输中途是 `receiver ran out of disk space during the transfer`）。Dart 词表认的是 `storage full`（中间是空格）和几个中文词，这两句都不命中，于是落到兜底“出了点问题”；同时连接行显示“连接已中断”。测试里用来代表这种情况的字符串 `磁盘空间不足（STORAGE_FULL）` 在产品代码里没有任何地方会生成，所以测试是绿的，真实文本却没被覆盖。这是文件传输里最常见、用户也最能自己解决的失败之一。修复建议：词表补 `storage_full`、`insufficient free space`、`ran out of disk space`；发送场景给专门文案（“对方的设备空间不足。请对方清理空间后重新配对再发送，会从断点续传”）；现有的“无法保存到所选文件夹……请在设置里更换保存文件夹”只用于接收场景；测试输入改用从 Rust 常量抄来的真实文本。

### W-N11（P2，产品，Android）等待阶段不保持常亮〔推断，未实测〕

〔代码〕W7.3 的常亮与“请保持在前台”的提示只在传输进行中生效。两个等待阶段没有覆盖：显示配对码等对方加入；已配对、等对方选文件。对方手输 36 位码通常超过半分钟，多数手机的默认熄屏时间也就是半分钟到一分钟；V2 的走查已经确认锁屏后几秒内传输即停住、进程被冻结。屏幕一灭，创建方无法应答配对请求，加入方看到的又是“这个码用不了”（W-N9）。修复建议：先在模拟器上复现（显示码后让屏幕自然熄灭，再从宿主加入），属实再改——把常亮和提示扩大到“码已显示”和“已配对未完成”两个状态，以码的有效期和配对闲置预算为上限。把应用切到后台去粘贴配对码的情况靠常亮解决不了，属于 O-1 的范围。

### W-N12（P2，测试）K1 走查脚本没有适配、没有重跑

〔代码〕K1（`k1_android_saf_test.dart`）驱动的正是“宿主 CLI 创建接收码，App 加入并作为发送方”——W7.1 弄坏的那个方向。批次 W 只删掉了其中选方向的那一步，没有再运行；如果运行过，W-N1 当场就会暴露。它的后半段（在首页点连接卡片、再点“选择文件”）是 W7.2 之前的流程，而现在发送方配对成功后应用会自动打开详情页并弹出来源选择，脚本很可能已经对不上〔推断〕；末尾还断言一句已经从产品里删掉的文案不存在，这条断言永远成立。复核方在 `da70e5f` 把它的方向选择步骤改了回去，同样没有运行。修复建议：按 W7.2 适配后在模拟器上跑通；以后凡是改了某条流程，就把驱动这条流程的全部走查脚本列进回归清单，没跑的写明“未重跑”。

### W-N13（P2，脚本，复核方改动）控制字符检查对回车符不生效

〔实测〕`0cc9baa` 加的规则声称能拦住“TAB、LF 以外的控制字符，含 CR”。但 `check()` 用 `read_text` 读文件，Python 会把 CR 和 CRLF 先转成 LF，规则根本见不到 CR：复核方用四个样例验证，单独的 CR 和 CRLF 经读文件这条路都是 0 条告警，响铃符 1 条。三条单元测试是把字符串直接传给函数，绕过了读文件这一步，所以一直是绿的。V 复核、状态表 V-N1 行和 W 交接 §1 里“含 CR”的说法不成立；批次 V 那次事故里“回车把一行拆开”的那一半，这条规则当时也拦不住。修复建议：按字节读入再解码（或以 `newline=""` 打开），并加一条经过读文件路径的测试。

### W-N14（P3，脚本，复核方改动）“路径分隔符”检查太窄

〔实测、代码〕`38a6f46` 加的规则只认两种形状：路径占位符后直接跟字母，以及一个写死的日志文件名。反斜杠后面跟 t 被展开成 TAB 的情况（例如以 t 开头的目录名）两条规则都拦不住，因为 TAB 是允许的；而仓库里的 Markdown 目前一个 TAB 都没有。修复建议：直接禁止 Markdown 里出现 TAB，覆盖面比现在的专用规则大；写死文件名的那一半可以删掉。

### W-N15（P3，契约与注释，复核方改动）

- `ffi-v2.md` 是冻结文件，修改需集成者核准。复核方在 `da70e5f` 改了其中一句，没有走核准；句子里还写进了界面做法和复核编号，这些不属于契约。建议由集成者改成只描述接口语义的写法，并在 `ak_task_join` 的 JSON 示例里补上可选的 `role` 字段——示例里一直没有它，这也是误读的来源之一。
- `w7_interaction_test.dart` 与 `home_flow_test.dart` 的文件头注释仍写着“加入面板没有方向选择、加入不带 role”，与现在的测试内容相反。

## 4. “免选方向”的正确做法

加入方的方向在现协议下只能由调用方声明，所以加入面板里那一步不能靠删掉来解决。审核 §4.3 已经给出了做法：首页两个主入口“发送文件”“接收文件”，**方向由用户一开始点的按钮决定，只声明一次**——

| 入口 | 主路径 | 次要入口 |
|---|---|---|
| 发送文件 | 先选文件，再生成码（创建方为发送方），对方加入后自动开始发送 | “对方已经给了你一个码？输入对方的码”（加入方为发送方，方向已知） |
| 接收文件 | 输入对方的码（加入方为接收方，方向已知） | “想让对方输入你的码？生成接收码”（创建方为接收方） |

四个组合里，方向都来自第一次点击，加入面板与生成码前都不再问。这是批次 X 的 X4。

备选做法（不建议）：被拒绝的加入不消耗码的兑换次数，所以理论上可以“先按接收方试，失败再按发送方试”。但统一的拒绝文本分不清是方向不对还是码无效，无效码会被多试一次，还要重新评估服务器的限速；不如 X4 干净。

## 6. 优化建议

不属于缺陷，按价值排序：

1. **启动耗时的测量**（W6）。Windows 上 3 秒多的冷启动里原生引导只占十几毫秒，剩下的时间还没有分开。建议在启动日志里补四个时间点：Dart `main` 入口、`runApp` 返回、首帧回调、任务服务启动完成；再用 `flutter create` 的空白工程在同一台机器上测一次作基线，并在排除杀毒软件实时扫描的目录里复测一次。三者能分清“引擎本身慢、我们的首帧慢、还是环境”。Android 上 `am start -W` 的结果失真，改用 logcat 里系统打印的 `Displayed` 行作首帧时间。
2. **看门狗与引擎的分工**（W-N2 的延伸）。连接是死是活由引擎说了算；Dart 一侧的计时只用来提示用户，不直接改终态。
3. **错误文案的测试用真实文本**（W-N10 的延伸）。分类测试的输入从 Rust 的常量与 `Display` 文本抄录，并注明出处；自造的字符串不能证明映射对真实错误有效。
4. **走查脚本的回归清单**（W-N12 的延伸）。在交接里维护一张表：每个走查脚本驱动哪条流程。批次改了哪条流程，就重跑表里对应的全部脚本。
5. **打包脚本**。`git status` 跑不了时现在只告警、照常打包，清单里也不留痕迹；建议在清单里记一行“工作区状态未核实”。
6. **契约示例补全**。`ak_task_join` 的示例补上可选 `role` 及缺省语义（W-N15）。

界面改版的整体建议见 [审核 §4](AUDIT_2026-11-22.zh-CN.md#4-界面设计方案)，本文不重复。

## 7. 过程上的观察

- **角色边界。** 复核方只做审核与计划，不改代码（所有者 2026-11-22 指示）。本轮的教训是：复核方既看不到设备，又能直接推分支，越界改动的风险全部落在没人验证的那一段。
- **先查现有测试，再读契约文字。** W-N1 的行为，仓库里有现成的测试写得清清楚楚；复核方写交接、执行方做改动时都只引用了契约里的一句话。
- **测试替身要和真实引擎同语义。** 假服务宽容的地方，正是真实路径出问题的地方（W-N7）；自造的错误文本也一样（W-N10）。
- **单元测试要走真实入口。** W-N13 里函数级的测试全绿，读文件的那一步却把要查的字符先吃掉了。
- **证据放在 `/tmp`。** 走查原始输出在执行方本机，复核方看不到，只能依赖 §8 里原样贴的关键行；做法保持，但结论依赖的关键行必须原样贴进 §8。
- **外部裁决。** 执行方应所有者要求请外部 agent（codex）复核，追改的三处都成立。其对 O-1、O-3、O-6 的“预审”不是所有者的决定。
